# Project Debug Rules (Non-Obvious Only)

- For debugging work involving FURS/eDavki technical specifications, request structures, certificates, signing, communication, or related integrations, first consult the official technical-specifications page at https://edavki.durs.si/edavkiportal/openportal/CommonPages/Opdynp/PageD.aspx?category=dpr_teh_spec and the direct PDF technical documentation at https://www.datoteke.fu.gov.si/dpr/files/TehnicnaDokumentacijaVer3.2.pdf; verify currency and distinguish official-documentation facts from diagnostic conclusions or recommendations.
- Use `specs/TehnicnaDokumentacijaVer3.2.txt` as the local searchable FURS v3.2 spec extract when debugging payload/schema/signing issues; regenerate from `specs/TehnicnaDokumentacijaVer3.2.pdf` with `pdftotext -layout` if needed, then confirm currency against the official sources.
- Run the test suite with `pytest` (132 tests). Replay tests in `tests/test_replay.py` are the strongest reproducer: they decode each official signed example in `specs/examples/`, rebuild it via the library, and assert structural equality + JSON-Schema validation. If replay fails, the wire format diverged.
- Exception classes (2.0+): `FURSError` base; `FURSValidationError` (also `ValueError`) for local rejection; `FURSConnectionError` (`.code` is the HTTP status string, `'REQUEST_FAILED'`, `'INVALID_RESPONSE'`, `'INVALID_SIGNATURE'`, or `'MISSING_RESPONSE_PUBLIC_KEY'`) for transport/decode failure; `FURSResponseError` for FURS-returned errors with `FURSSchemaError` (S001/S002), `FURSSignatureError` (S003), `FURSCertificateError` (S004 unknown / S005 tax-mismatch / S007 revoked / S008 expired), `FURSBusinessPremiseError` (S006 premise not registered), `FURSSystemError` (S100 transient, `is_retryable=True`), and `FURSServerError` (everything else) subclasses. Lookup is case-insensitive (production has emitted lower-case `s002`). The 1.x `FURSException`/`ConnectionException`/`ConnectionTimedOutException` no longer exist.
- Retry-decision diagnostic: `FURSResponseError.is_retryable` is `True` only for `FURSSystemError` (S100). When a caller reports "I retried on `FURSCertificateError` and got the same error" — that's expected; cert-bound failures are deterministic. Point them at the specific subclass (`FURSCertificateError` for cert/tax-mismatch, `FURSBusinessPremiseError` for premise registration) and the corresponding fix path.
- Pydantic `ValidationError` wraps each field error; inspect `exc.errors()` for the structured list (loc, type, msg) to find the offending field. Common gotchas: passing a `float` amount → "float is rejected to avoid silent IEEE-754 precision loss"; passing a naive datetime → "datetime must be timezone-aware".
- The amount round-trip check rejects values close to ±100T because `float(Decimal('99999999999999.99'))` silently becomes `99999999999999.98`. If a legitimate huge amount is failing, verify the magnitude is the issue before relaxing the validator — the truncated float would diverge from the ZOI input string.
- Datetimes are auto-converted to `Europe/Ljubljana` (`models.LJUBLJANA`) before formatting. If a debugged payload shows a different `IssueDateTime` than the caller expected, check the input timezone — UTC at 08:00 in late April becomes 10:00 CEST in the wire format. Same holds for ZOI signing input and `prepare_printable` output.
- Per-record batch errors raise `FURSBatchError`; check `exc.record_errors[record_number]` (each value is a `FURSResponseError` subclass) and `exc.successes` (records that succeeded — their EORs should be persisted before any retry).
- TLS/response-verification debugging: `FURSTLSVerificationDisabledWarning` indicates `verify_tls=False`; `FURSResponseChainNotVerifiedWarning` indicates the response was decoded in `'x5c-untrusted'` mode. The latter validates the JWS signature against the cert in the `x5c` header AND its validity window, but does NOT validate the chain — chain validation requires `verify_furs_response=True` with a pinned `furs_response_public_key`.
- TLS handshake debugging: `_load_ssl_context_with_client_cert` pins `minimum_version=TLSv1_2` and `set_ciphers(FURS_TLS_CIPHERS)` regardless of the `verify_tls` value (per spec sec. 2 / 6.2). If a handshake suddenly fails after a FURS spec rotation, suspect cipher mismatch first: the surveillance test `test_furs_tls_cipher_list_rotation_surveillance` will warn yellow before 2026-05-12 and fail red after — that's the canonical reminder to re-verify `FURS_TLS_CIPHERS` against the current `TehnicnaDokumentacijaVer*.pdf` sec. 6.2 lists. To inspect what OpenSSL actually advertises: `ctx.get_ciphers()` (TLS 1.2 + 1.3 combined; TLS 1.3 names start with `TLS_` and are not affected by `set_ciphers`).
- `Connector.post` parses non-200 status as `FURSConnectionError(code=str(status))`. Inspect `response.text` (truncated to 500 chars in the message) for FURS HTML/text body when status is 4xx/5xx. Empty/non-JSON body raises `FURSConnectionError(code='INVALID_RESPONSE')`.
- Mocked HTTP for offline reproduction: tests use `httpx.MockTransport(handler)`. See `tests/test_transport.py::_connector_with_mock_transport` and `tests/test_api.py::_client_with_handler` for templates. The mock client needs `base_url=FURS_TEST_ENDPOINT` set or relative paths fail at URL parsing.
- In-memory client cert loader (`_load_ssl_context_with_client_cert`): leaks of `*.pem` files in `/tmp` indicate a regression — the load → unlink cycle is asserted by `tests/test_transport.py::test_in_memory_cert_loader_does_not_leave_temp_files`.
- Default endpoint: `production=False` → `FURS_TEST_ENDPOINT` (`https://blagajne-test.fu.gov.si:9002`). `production=True` → `FURS_PRODUCTION_ENDPOINT` (`:9003`). There is no override.
- The `demos/` directory is 1.x-shaped legacy code and will not run against 2.0; do not use it for repro.
