# Project Architecture Rules (Non-Obvious Only)

- For architectural work involving FURS/eDavki technical specifications, request structures, certificates, signing, communication, or related integrations, first consult the official technical-specifications page at https://edavki.durs.si/edavkiportal/openportal/CommonPages/Opdynp/PageD.aspx?category=dpr_teh_spec and the direct PDF technical documentation at https://www.datoteke.fu.gov.si/dpr/files/TehnicnaDokumentacijaVer3.2.pdf; verify currency and clearly distinguish official-documentation facts from architectural inferences or recommendations.
- Use `specs/TehnicnaDokumentacijaVer3.2.txt` for repository-local searches of the FURS v3.2 spec; the source PDF is `specs/TehnicnaDokumentacijaVer3.2.pdf`. The official JSON schemas are mirrored 1:1 by pydantic models in `furs_fiscal/models.py`; treat `specs/schemas/FiscalVerificationSchema*.json` as the single source of truth and the models as the typed projection.
- Module layout (2.0): `furs_fiscal/api.py` (`FURSClient` — application entry point), `furs_fiscal/models.py` (pydantic wire models + `wrap_*` envelope helpers), `furs_fiscal/zoi.py` (pure ZOI/printable-QR functions, no transport dependency), `furs_fiscal/transport.py` (`Connector` — httpx + in-memory mTLS + JWS sign/verify), `furs_fiscal/exceptions.py` (granular hierarchy). The 1.x `base_api.py`/`connector.py` split no longer exists.
- `Connector` is private. Application code goes through `FURSClient.submit_invoice`/`submit_sales_book_invoice`/`submit_business_premise`/`submit_invoice_batch`/`submit_business_premise_batch`. Endpoint paths are constants in `api.py` (`PATH_INVOICE`, `PATH_INVOICE_BATCH`, `PATH_BUSINESS_PREMISE`, `PATH_BUSINESS_PREMISE_BATCH`).
- Endpoint selection is still the boolean `production` flag (`9003` production vs `9002` test); there is no injectable base URL without modifying `Connector`.
- Mutual TLS uses `ssl.SSLContext.load_cert_chain` from PEMs that exist on disk only for the duration of a single `mkstemp`→write→load→unlink cycle inside `_load_ssl_context_with_client_cert`. The connector's lifetime never sees the key on disk. Reintroducing persistent temp files is a security regression.
- Response signature verification is wired in via `Connector._decode_response_token` with three modes: `'x5c-untrusted'` (default), `True` (pinned key, MITM-resistant), `False` (off). `'x5c-untrusted'` is "signature self-consistency" — the cert in the JWS `x5c` header is what verifies the signature, so it must be paired with `verify_tls` against SIGOV-CA for real protection.
- Mutual-exclusion and `oneOf` schema rules are enforced by `@model_validator(mode='after')` on the relevant pydantic models (`Invoice` operator fields, `BPIdentifier`, `VendingMachine`, `SoftwareSupplier`). Adding new schema constraints belongs there, not in `FURSClient`.
- Header (MessageID + DateTime) is auto-generated by `Header` defaults (`uuid.uuid4()` and `datetime.now(LJUBLJANA)`). The `wrap_*` helpers in `models.py` instantiate `Invoice/SalesBookInvoice/BusinessPremise` request envelopes with a fresh Header by default — callers should not pre-build Headers unless they have a specific reason (e.g. retrying with the same MessageID for idempotency).
- Batch envelope construction lives in `models.wrap_invoice_batch` / `wrap_business_premise_batch`. They enforce the spec's 2..500 record range and assign sequential `RecordNumber` values starting at 1.
- Per-record batch errors are aggregated in `FURSClient._collect_record_replies` into `FURSBatchError(record_errors, successes)`. Successful records are preserved on the exception so callers can persist EORs without resubmitting.
- ZOI is intentionally a pure-function module (`furs_fiscal/zoi.py`) so it can be used standalone (e.g. by an offline POS terminal that holds only the private key, not a full client). `FURSClient.calculate_zoi` is a thin convenience wrapper.
