# Project Documentation Rules (Non-Obvious Only)

- For explanatory or documentation work involving FURS/eDavki technical specifications, request structures, certificates, signing, communication, or related integrations, first consult the official technical-specifications page at https://edavki.durs.si/edavkiportal/openportal/CommonPages/Opdynp/PageD.aspx?category=dpr_teh_spec and the direct PDF technical documentation at https://www.datoteke.fu.gov.si/dpr/files/TehnicnaDokumentacijaVer3.2.pdf; verify currency and clearly distinguish official-documentation facts from agent inferences or recommendations.
- Use `specs/TehnicnaDokumentacijaVer3.2.txt` for quick local citation/search of the FURS v3.2 spec; the source PDF is `specs/TehnicnaDokumentacijaVer3.2.pdf`. Always verify currentness against the official page/PDF for specification-sensitive answers.
- The library is **2.0** — a complete rewrite of 1.x. When answering "how do I do X", point users at `README.md` (which has the migration table from 1.x) and the typed `FURSClient` API, not the legacy `FURSInvoiceAPI`/`FURSBusinessPremiseAPI` classes.
- The most authoritative usage examples are in `tests/` (88 tests covering models, ZOI, transport, full client flows, and replay against official samples). `tests/test_replay.py` in particular shows the canonical way to construct each message type because it must produce payloads byte-equivalent to the FURS-published JWS examples in `specs/examples/`.
- The `demos/` directory still contains 1.x-shaped scripts and is NOT updated for 2.0; treat those as historical and prefer the README quick-start as the reference example.
- Bundled certs: `furs_fiscal/certs/test_certificate.pem` is shipped as `package_data` but the 2.0 transport does not use it for trust decisions — `verify_tls=True` uses the system CA store by default; pinning is opt-in via passing a path string.
- FURS protocol values exposed as pydantic `Literal` types: `numbering_structure` is `"B"` (per electronic device, default in spec examples) or `"C"` (centrally at the level of business premises). `BPIdentifier.premise_type` is `"A"`/`"B"`/`"C"` for movable, `VendingMachine.vending_premise_type` is `"D"`/`"E"`/`"F"` for vending machines.
- Datetime semantics question to expect: "why does my IssueDateTime look different from what I passed?" → models auto-convert all timezone-aware datetimes to `Europe/Ljubljana` before formatting per spec text R_3.2 / P_2.0; passing a naive datetime raises `pydantic.ValidationError`.
- Amount semantics question to expect: "why does the library reject my float?" → IEEE-754 silently corrupts decimals (`float(0.1) + float(0.2) != 0.3`). The library accepts only `Decimal`, `int`, or `str` so the on-the-wire amount always equals the value hashed into ZOI. There is also an upper-bound round-trip check that rejects values close to the schema's exclusive ±100T limit which would lose cents in float64.
- Batch question to expect: "what happens when one record in a batch fails?" → `FURSBatchError` is raised with `.record_errors` (per-record `FURSResponseError` subclass keyed by `RecordNumber`) and `.successes` (the EORs of records that succeeded — persist these so callers don't resubmit them).
- Error-handling question to expect: "which exception do I catch for code Sxxx?" → spec sec. 4 codes route through `from_furs_error` to specific classes: S001/S002 → `FURSSchemaError`, S003 → `FURSSignatureError`, S004/S005/S007/S008 → `FURSCertificateError` (unknown / tax-mismatch / revoked / expired digital cert), S006 → `FURSBusinessPremiseError`, S100 → `FURSSystemError`, anything else → `FURSServerError`. Lookup is case-insensitive. The README "Exception Hierarchy" section is the user-facing reference; point users there.
- Retry question to expect: "should I retry on this exception?" → `FURSResponseError.is_retryable` (`True` only on `FURSSystemError`/S100 today). The library does **not** auto-retry — it surfaces the signal and lets callers decide. For `FURSConnectionError`, retry is a transport-layer call: 5xx HTTP statuses and timeouts are usually retryable, schema/signature errors bubbling up via `FURSResponseError` are not.
- TLS-pinning question to expect: "why is my custom CA bundle / TLS 1.0 device rejected?" → `Connector` always pins `minimum_version=TLSv1_2` and the AEAD-RSA cipher subset (`FURS_TLS_CIPHERS`) per spec sec. 2 / 6.2, even when `verify_tls=False`. This is intentional and not configurable from `FURSClient` — relaxing it requires editing `transport.py` with a spec citation.
